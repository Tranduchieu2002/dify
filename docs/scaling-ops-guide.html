Dify Scaling & Test Ops

Start, scale, benchmark, and monitor Dify workers and sandbox containers.

Start minimal local stack

01

Start middleware (postgres + redis + sandbox + weaviate)

cd docker
docker compose --env-file middleware.env -f docker-compose.middleware.yaml -p dify up -d \
  db_postgres redis sandbox ssrf_proxy weaviate plugin_daemon
02

Run DB migrations

cd api && uv run flask db upgrade
03

Start API server (handles HTTP + WebSocket via socketio_app)

# Increased worker-connections to avoid greenthread starvation
SERVER_WORKER_CONNECTIONS=100 dev/start-api > /tmp/dify-api.log 2>&1 &
04

Start Celery worker

dev/start-worker -q workflow,workflow_based_app_execution,pipeline,priority_pipeline \
  > /tmp/dify-worker.log 2>&1 &
05

Start beat scheduler (required for schedule-trigger workflows)

dev/start-beat > /tmp/dify-beat.log 2>&1 &
06

Verify everything is healthy

# API
curl http://localhost:5001/health

# Middleware containers
docker compose -p dify ps

# Worker ping
cd api && uv run celery -A app.celery inspect ping

Docker Compose scaling overlay

The file docker/docker-compose.scaling.yaml is a Compose overlay that splits workers by queue group, adds a sandbox load balancer, and adds Flower. Always compose it on top of the base file.

# Start full scaled stack (2 workflow workers, 2 sandboxes)
cd docker
docker compose \
  -f docker-compose.yaml \
  -f docker-compose.scaling.yaml \
  --scale sandbox=2 \
  up -d

# Scale workflow workers to 3 at runtime (no restart)
docker compose \
  -f docker-compose.yaml \
  -f docker-compose.scaling.yaml \
  up -d --scale worker-workflow=3 --no-recreate

# Scale sandbox to 3 at runtime
docker compose \
  -f docker-compose.yaml \
  -f docker-compose.scaling.yaml \
  up -d --scale sandbox=3 --no-recreate
Important When scaling sandbox, the sandbox-lb nginx container distributes requests via DNS round-robin to all sandbox replicas. Point CODE_EXECUTION_ENDPOINT=http://sandbox-lb:8194 in your .env.

Local multi-worker setup

When developing locally, start multiple workers with distinct --hostname flags so Flower and celery inspect can tell them apart.

QUEUES="workflow,workflow_based_app_execution,pipeline,priority_pipeline"

# Worker 1
cd api && uv run celery -A app.celery worker \
  -P gevent -c 4 -Q $QUEUES \
  --hostname=worker1@%h \
  --prefetch-multiplier=1 \
  --loglevel=INFO \
  > /tmp/dify-worker1.log 2>&1 &

# Worker 2
uv run celery -A app.celery worker \
  -P gevent -c 4 -Q $QUEUES \
  --hostname=worker2@%h \
  --prefetch-multiplier=1 \
  --loglevel=INFO \
  > /tmp/dify-worker2.log 2>&1 &

# Worker 3
uv run celery -A app.celery worker \
  -P gevent -c 4 -Q $QUEUES \
  --hostname=worker3@%h \
  --prefetch-multiplier=1 \
  --loglevel=INFO \
  > /tmp/dify-worker3.log 2>&1 &

# Confirm all 3 are online
cd api && uv run celery -A app.celery inspect ping
Why distinct hostnames? Workers running on the same machine default to the same hostname (celery@hostname), causing conflicts in Flower and in Celery's internal worker registry. Always set --hostname=workerN@%h.

Inspect workers (Docker)

# List all workers online
docker compose exec worker celery -A celery_entrypoint inspect ping

# See active tasks per worker right now
docker compose exec worker celery -A celery_entrypoint inspect active

# See which queues each worker listens to
docker compose exec worker celery -A celery_entrypoint inspect active_queues

# Worker stats (concurrency, pool, total processed)
docker compose exec worker celery -A celery_entrypoint inspect stats \
  | grep -E "hostname|total|concurrency|prefetch"

# From the local venv (works against any running cluster)
cd api && uv run celery -A app.celery inspect ping
cd api && uv run celery -A app.celery inspect active_queues

Standalone Docker workers (attach to existing middleware)

Use docker/docker-compose.workers.yaml to spin up dedicated worker containers that join the existing middleware network (dify_default + dify_ssrf_proxy_network). Middleware must already be running under project dify.

# Copy api/.env and override host-based addresses for containers
# Key overrides already set in docker/worker-docker.env:
#   REDIS_HOST=redis  REDIS_PORT=6379
#   CELERY_BROKER_URL=redis://:difyai123456@redis:6379/1
#   DB_HOST=db_postgres  DB_PORT=5432
#   CODE_EXECUTION_ENDPOINT=http://ssrf_proxy:8194
#   PLUGIN_DAEMON_URL=http://plugin_daemon:5002
#   ENABLE_OTEL=false

# Start 1 workflow worker + dataset worker + ops worker + Flower
docker compose -f docker/docker-compose.workers.yaml -p dify-workers up -d

# Scale workflow workers to 3 (live, no restart)
docker compose -f docker/docker-compose.workers.yaml -p dify-workers \
  up -d --scale worker-workflow=3 --no-recreate

# Verify all workers registered
cd api && uv run celery -A app.celery inspect ping --timeout 5 2>&1 | grep -E "^->|nodes online"

# Tear down
docker compose -f docker/docker-compose.workers.yaml -p dify-workers down
CODE_EXECUTION_ENDPOINT Docker workers must reach the sandbox through ssrf_proxy:8194, not directly to sandbox:8194. The ssrf_proxy acts as the reverse proxy and SSRF protection layer. Setting CODE_EXECUTION_ENDPOINT=http://ssrf_proxy:8194 is correct for any worker running inside dify_default network.
Flower port conflict The standalone compose starts Flower on port 5556 (not 5555) to avoid conflicting with a locally-running Flower. Override with FLOWER_PORT=5557 docker compose ….

Sandbox scaling

# Check sandbox health (proxied via ssrf_proxy on :8194)
curl http://localhost:8194/health

# Scale to 3 sandboxes (Docker Compose, via overlay)
docker compose -f docker-compose.yaml -f docker-compose.scaling.yaml \
  up -d --scale sandbox=3 --no-recreate

# Confirm requests spread across replicas
docker compose logs sandbox-lb --follow
Routing architecture Workers never call sandbox directly. The correct path is:
worker → ssrf_proxy:8194 (reverse proxy + SSRF protection) → sandbox:8194

For local processes: CODE_EXECUTION_ENDPOINT=http://localhost:8194 (ssrf_proxy exposed on host).
For Docker workers on dify_default: CODE_EXECUTION_ENDPOINT=http://ssrf_proxy:8194.

To scale sandbox, the sandbox-lb nginx container must sit between ssrf_proxy and sandbox replicas, which requires updating ssrf_proxy's SANDBOX_HOST=sandbox-lb env var and recreating it.

Benchmark — available workflows

KeyNameDescriptionTypical latency
fast bench-fast-passthrough Start → End, no compute. Tests raw queue throughput. ~300ms
code bench-code-execution One code node (reverse words). Tests sandbox single call. ~400–900ms
heavy bench-heavy-wait 3 code nodes with CPU work + sleep (500+200+100ms). Tests sustained sandbox + worker load. 3–6s

API keys are hardcoded in bench-run.py. Re-run python3 dify-workflow.py list to find app IDs if you recreate them.

Benchmark — run commands

Local (requires Python 3.12+)

# Fast passthrough — 10 runs, 5 concurrent
python3 bench-run.py --workflow fast -n 10 -c 5

# Code execution — 20 runs, 10 concurrent
python3 bench-run.py --workflow code -n 20 -c 10

# Heavy (3-step wait) — stress test
python3 bench-run.py --workflow heavy -n 20 -c 8

# Run all suites back to back
python3 bench-run.py --workflow all -n 15 -c 6

# Push to 30 concurrent to see queue build up
python3 bench-run.py --workflow heavy -n 50 -c 30

Via Docker — dev/bench (no Python required)

# Same flags, runs python:3.12-slim in Docker with --network host
dev/bench --workflow heavy -n 20 -c 8
dev/bench --workflow all  -n 15 -c 6

# Target a different API (e.g. staging)
DIFY_BASE_URL=http://staging:5001 dev/bench --workflow heavy -n 10 -c 4

# Override Redis connection (bench-run.py env vars)
#   DIFY_BASE_URL   API base URL            (default: http://localhost:5001)
#   REDIS_HOST      Redis hostname           (default: localhost)
#   REDIS_PORT      Redis port               (default: 6380)
#   REDIS_PASSWORD  Redis auth password      (default: difyai123456)
How dev/bench works Uses --network host on Linux/WSL2 so the container shares localhost — no port mapping needed. On macOS it switches to bridge mode and sets host.docker.internal automatically. Redis queue depth is checked via raw TCP RESP (no Docker socket required).

Schedule trigger (run every N minutes)

# Beat is required — without it, scheduled triggers never fire
dev/start-beat > /tmp/dify-beat.log 2>&1 &

# Verify beat is polling
tail -f /tmp/dify-beat.log
# → "Scheduler: Sending due task workflow_schedule_poller"

In the workflow editor: replace the Start node with a Schedule Trigger node → choose Cron mode → enter * * * * * for every minute. Publish, then beat dispatches it automatically.

Run exactly one beat process Running two beat processes causes duplicate task dispatch. Beat is not horizontally scalable — only one instance per cluster.
