01

Split Celery workers by queue group

The existing entrypoint already supports CELERY_WORKER_QUEUES to override which queues a container consumes. Add three worker service definitions — replace the single worker service in docker-compose.yaml.

worker-workflow

Scale this one up first under load.

  • workflow
  • workflow_based_app_execution
  • pipeline
  • priority_pipeline

worker-dataset

Isolated so indexing can't block runs.

  • dataset
  • dataset_summary
  • priority_dataset

worker-ops

Low-volume background jobs.

  • mail, ops_trace, conversation
  • api_token, plugin, retention
  • schedule_poller/executor
  • trigger_refresh_*
docker/docker-compose.yaml — worker section replacement
  # ── Workflow worker (scale this horizontally)
  worker-workflow:
    <<: *shared-worker-config
    environment:
      <<: *shared-api-worker-env
      MODE: worker
      CELERY_WORKER_QUEUES: workflow,workflow_based_app_execution,pipeline,priority_pipeline
      CELERY_WORKER_CONCURRENCY: ${WORKFLOW_WORKER_CONCURRENCY:-4}
      CELERY_PREFETCH_MULTIPLIER: 1
      MAX_TASKS_PER_CHILD: 50
    deploy:
      replicas: ${WORKFLOW_WORKER_REPLICAS:-2}

    # ── Dataset worker (keep at 1 unless indexing is a bottleneck)
  worker-dataset:
    <<: *shared-worker-config
    environment:
      <<: *shared-api-worker-env
      MODE: worker
      CELERY_WORKER_QUEUES: dataset,dataset_summary,priority_dataset
      CELERY_WORKER_CONCURRENCY: ${DATASET_WORKER_CONCURRENCY:-2}
      CELERY_PREFETCH_MULTIPLIER: 1

    # ── Ops worker (mail, triggers, retention, plugins)
  worker-ops:
    <<: *shared-worker-config
    environment:
      <<: *shared-api-worker-env
      MODE: worker
      CELERY_WORKER_QUEUES: mail,ops_trace,app_deletion,conversation,api_token,plugin,workflow_storage,retention,schedule_poller,schedule_executor,triggered_workflow_dispatcher,trigger_refresh_publisher,trigger_refresh_executor
      CELERY_WORKER_CONCURRENCY: ${OPS_WORKER_CONCURRENCY:-2}
Why PREFETCH_MULTIPLIER=1 The default Celery prefetch is 4. Each worker greedily reserves tasks before processing them, so one slow workflow node can lock up 4 task slots. Setting it to 1 means each worker holds exactly one task at a time — fairer queue draining under mixed load.
02

Scale sandbox with an internal load balancer

Sandbox has no host-port mapping so docker compose up --scale sandbox=3 works — but then CODE_EXECUTION_ENDPOINT still points at a single container name. Add a minimal nginx as a load balancer on ssrf_proxy_network.

docker/sandbox-lb.conf
upstream sandbox_pool {
    least_conn;
    server sandbox:8194;      # Docker resolves all replicas via DNS round-robin
}

server {
    listen 8194;

    location / {
        proxy_pass         http://sandbox_pool;
        proxy_read_timeout 90s;
        proxy_send_timeout 30s;
        proxy_set_header   Host $host;
    }

    location /health {
        access_log off;
        return 200 "ok\n";
    }
}
docker/docker-compose.yaml — sandbox section
  sandbox:
    image: langgenius/dify-sandbox:0.2.15
    networks: [ssrf_proxy_network]
    deploy:
      replicas: ${SANDBOX_REPLICAS:-2}
      # Remove the static port mapping here if present — replicas need it gone

  sandbox-lb:
    image: nginx:alpine
    networks: [ssrf_proxy_network, default]
    volumes:
      - ./sandbox-lb.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [sandbox]
    restart: always
.env — point api/worker at the lb
CODE_EXECUTION_ENDPOINT=http://sandbox-lb:8194
SANDBOX_REPLICAS=2
WORKFLOW_WORKER_REPLICAS=2
WORKFLOW_WORKER_CONCURRENCY=4
Deploy flag deploy.replicas is honored by Docker Compose v2 in plain docker compose up. In Swarm mode (docker stack deploy) it works the same way. You do NOT need Kubernetes for this.
03

Celery knobs to tune for workflow load

Env varRecommended valueWhy
CELERY_PREFETCH_MULTIPLIER 1 Prevent task hoarding. Each worker slot holds exactly one task — fairer under mixed workflow sizes.
CELERY_WORKER_CONCURRENCY
(workflow workers)		 4–8 Workflow tasks are I/O-heavy (LLM calls). 4–8 gevent greenthreads per container is a good start; increase until CPU is the bottleneck.
MAX_TASKS_PER_CHILD 50 Already the default. Recycles worker processes to prevent memory leaks from long-running sessions.
CELERY_WORKER_CLASS / POOL gevent Already the default. Gevent's green-thread pool handles async LLM streaming without forking — ideal for workflow tasks.
CELERY_AUTO_SCALE false Pin concurrency at a known value per container; scale via replicas, not autoscale — easier to reason about under load.
CODE_EXECUTION_POOL_MAX_CONNECTIONS 100 × sandbox replicas Default 100 is per-process. With 2 sandbox replicas and 2 worker replicas, the lb can handle 200 concurrent sandbox calls.
04

Add Flower — Celery monitoring UI

Flower gives you a real-time view of queue depths, active tasks per worker, and task history. Add it to the compose stack.

docker/docker-compose.yaml — append
  flower:
    image: mher/flower:2.0
    command: celery flower --broker=${CELERY_BROKER_URL} --port=5555
    environment:
      CELERY_BROKER_URL: ${CELERY_BROKER_URL:-redis://:difyai123456@redis:6379/1}
    ports:
      - "5555:5555"
    networks: [default]
    depends_on: [redis]
    restart: always

Access Flower at http://localhost:5555. You can see each worker-workflow container as a separate node, its active task count, and queue depth in real time.

05

How to know it's working

  • 1
    All workers register on startup Run this — you should see three separate worker hostnames (worker-workflow@…, worker-dataset@…, worker-ops@…) respond to the ping.
    docker compose exec worker-workflow celery -A celery_entrypoint inspect ping
  • 2
    Each worker only consumes its assigned queues The active_queues report must NOT show dataset on the workflow worker, or workflow on the ops worker.
    docker compose exec worker-workflow celery -A celery_entrypoint inspect active_queues
  • 3
    Sandbox LB distributes load across replicas Hit the sandbox health endpoint multiple times — you should see different container IDs in nginx access logs.
    docker compose logs sandbox-lb --follow
    Then fire a Code node workflow and watch requests spread across the sandbox containers.
  • 4
    Queue depth stays low under sustained load Watch Redis queue length for the workflow queue. If it grows continuously, add another worker-workflow replica.
    watch -n 2 'docker compose exec redis redis-cli llen workflow'
    Target: queue length below 10 under normal load. Above 50 = add a replica.
  • 5
    Active task count scales with replicas Open Flower at http://localhost:5555. Fire 20 concurrent workflow runs (use the existing test-workflow.yml). The Active column for each worker-workflow node should fill up proportionally — not one node saturated while others idle.
  • 6
    Dataset jobs don't delay workflow runs Trigger a large dataset re-index while running workflows concurrently. Workflow run times should be unaffected. Before this split, they would slow down because one worker pool served both.
  • 7
    Existing Grafana/Loki stack shows throughput Your docker-compose.logging.yaml already runs Loki + Grafana. Import a Celery task latency dashboard in Grafana. Look for:
    — P95 task runtime for workflow queue tasks staying flat as replicas scale.
    — No error spikes in the API container logs during scale-up.
    docker compose -f docker-compose.yaml -f docker-compose.logging.yaml up -d

Minimal quick-start sequence

Step-by-step
# 1. Apply compose changes, then bring up with 2 workflow workers + 2 sandboxes
WORKFLOW_WORKER_REPLICAS=2 SANDBOX_REPLICAS=2 \
  docker compose up -d --scale sandbox=2

# 2. Confirm all three worker groups are alive
docker compose ps | grep worker

# 3. Verify queue assignments
docker compose exec worker-workflow-1 \
  celery -A celery_entrypoint inspect active_queues

# 4. Watch queue depth live
watch -n 2 'docker compose exec redis redis-cli llen workflow'

# 5. Open Flower dashboard
open http://localhost:5555

# 6. Fire test workflow runs (import test-workflow.yml in the UI, run ×10)
